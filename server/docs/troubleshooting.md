# 排障手册

**排查第一步永远是看控制台的「实时日志」分页** —— 客户端报的错通常很含糊，
而日志会直接告诉你请求有没有到、上游返回了什么。

<http://127.0.0.1:8788/console> → 实时日志

---

## 一、鉴权类

### `401 API Key 不正确`

客户端填的密钥和 `config.json` 里的 `apiKey` 不一致。

- 启动时终端会打印它的**掩码**形式（`sk-wb-1a2b3c…f9e8`），可以据此核对
- 如果 `apiKey` 是数组，**数组里任意一个都有效**
- 改过 `config.json` 后**必须重启服务**才生效

### `401 尚未登录`

该站点没有可用凭证：

```bash
node login.mjs --list           # 看哪个站点没登录
node login.mjs --site intl-cli  # 登录缺的那个
```

### `401 登录态失效`

该站点的 `refreshToken` 已过期。重新登录该站点即可。

---

## 二、额度类

### `402 额度不足`

该站点的剩余积分用完了。

> **国内版和国际版的额度不通用**，各自独立。一边用完可以切到另一边：
> 在控制台「模型与切换」里换默认模型，或用站点前缀（`intl-cli/xxx`）。

```bash
node status.mjs    # 看各站点还剩多少
```

### `429 限流`

上游限流。稍后重试，或降低并发。

> 本项目自己也有一层**滑动窗口限流**（防止客户端 bug 造成失控重试打爆上游）。
> 如果 429 是本服务返回的，响应头会带 `Retry-After`。
> 阈值在 `config.json` 的 `rateLimit` 段，默认很宽松，正常使用碰不到。

## 三、路径与协议类

### `404 未知路径 POST /v1/messages/chat/completions`

客户端把路径拼重复了（它自己补了 `/v1/messages`，而你又填了带 `/chat/completions` 的完整地址）。

- 服务端已做**后缀容错**，多数情况能自动识别
- 若仍报错：把客户端里的地址改成**基础地址** `http://127.0.0.1:8788/v1`

### 带不带 `/v1` 前缀？

**两种都认。** 服务端按路径段匹配，`/v1/chat/completions` 和 `/chat/completions` 都能命中。

### `400 Illegal API invocation from an unapproved channel`

上游识别出了客户端 system 提示词的**指纹**。

**v1.2.0 起已自动剥离**，正常情况下不会再遇到。若遇到：

- 先确认版本（`package.json` 的 `version`）
- 或把 `config.json` 的 `stripClientFingerprint` 显式设为 `true`

### `model xxx is only available for authorized users`

该模型你的账号没有权限 —— 不是配置问题，换一个模型即可：

```bash
node ask.mjs --list    # 看当前账号实际能用哪些
```

## 四、上下文类

### 长会话突然 `400 prompt is too long`

现在内置了滑动窗口压缩：从**最老**的消息开始丢，至少保留最近 4 条，
`tool_calls` 与其 `tool` 结果**同生共死**（只删一半上游会报 tool_call_id 找不到）。

若仍在触发，检查 `config.json`：

```jsonc
{
  "context": {
    "enabled": true,
    "reserveForOutput": 4096,
    "minKeepMessages": 4,
    "safetyRatio": 0.95
  }
}
```

> ⚠️ 上游在报错信息里给的「上限数字」**不可靠**。
> 实测同一个模型 34 万字符（约 18 万 token）明明能正常返回 200。

### 同样是超限，上游有两种报法

| 上游返回 | 代理的处理 |
|---|---|
| `11115` `prompt is too long: N tokens > M maximum` | 能解析出数字，按比例收缩后重试 |
| `11133` `Invalid request parameters` + `extError.model_param_invalid` | 没有 token 数字，**同样按超限处理**（带守卫：已知上限证明体积合规时不误判） |

第二条以前不被识别 —— 任何「too long」关键词都匹配不到，压缩完全不触发，
请求直接硬失败。实测 250 万字符触发过，而 100 万字符仍是 200。

> 另外：内置的预压缩只在**知道该模型上限**时才生效。上限来自两处 ——
> 站点动态目录里的 `contextWindow`，或站点内置清单 `seedModels[].contextWindow`。
> 国际版（`intl-work`）拉不到动态目录，所以它的内置清单里**必须写上 `contextWindow`**，
> 否则预压缩形同虚设：每个长请求都要先撞一次 400 再重试，白等 20~30 秒。

### 工具定义也算上下文，而且常常是大头

预算按**整个请求体**算：`messages` **加上** `tools` / `functions`。裁剪只能动 `messages`，
工具定义压不动，所以额度是先扣掉工具那一份再给对话用。

agent 客户端（DSH / Codex 等）带进来的工具 schema 可以占掉几十万 token。
这时如果只按 `messages` 估算，就会以为「装得下」而放行，结果上游回
`400 Invalid request parameters`；而重试只会反复压 `messages`
（实测 454711 → 229754 → 116101 → 58682）却怎么都压不下去 —— 大头根本不在对话里。

> 如果日志出现「工具定义约 N tokens，已吃满上下文上限」，说明该模型剩下的额度
> 几乎全被工具占满，只能精简客户端启用的工具 / MCP 数量，或换上下文更大的模型。
> 所以本项目把它当**信号**用，走相对收缩重试，而不是直接信那个数字。

### 回答被截断

上游把「思考」也计入输出 token。在客户端的高级配置里**调大输出上下文窗口**。

## 五、启动类

### `端口 8788 已被占用`

已经有一个实例在跑了：

```bash
node status.mjs    # 查看状态
node stop.mjs      # 优雅停止
```

或改 `config.json` 里的 `port`。

### `config.json 不是合法 JSON`

手改配置时漏了/多了逗号，或用了单引号（**JSON 只认双引号**）。

> 服务**不会覆盖**你的配置文件，所以改坏了不会丢数据 —— 修好逗号重启即可。

### 服务起来了但控制台打不开

控制台只接受**本机来源**（这是刻意设计：防止浏览器里的恶意页面跨站窃取会话令牌）。
如果你通过某种代理转发访问，会被拒。

正确做法：直接在跑服务的那台机器上打开 <http://127.0.0.1:8788/console>，
或用 `console-open.mjs`。

## 六、账号池

### 号池里某个账号反复失败

控制台「账号登录」分页可以看到每个账号的状态、失败次数、最后错误、冷却到期时间。

| 情况 | 行为 |
|---|---|
| 额度耗尽（429 / `insufficient credits`） | 标记为耗尽，**6 小时**后自动重试 |
| `401` / `403` | 先原地刷新该账号 token，仍失败才换号 |
| `5xx` / 网关错误 | 按 `30s → 2m → 10m → 30m` 阶梯冷却，之后换号 |
| 全站耗尽 | 如果另一个站点也提供该模型，自动降级过去；降级优先选**还有可用账号**的站点，不会从一个死站换到另一个死站 |
| 该站点只有一个账号且已耗尽 | 耗尽状态记在**内存**里（不建池文件，重启即清空），路由据此避开它；重新登录换号后自动失效 |
| `403` `11140 request illegal` | 多半是**账号被风控**：同样的内容换个账号就正常，换站点也一样拒。禁用该账号后，反代会在发送前改派到还有额度的站点 |
| 客户端写死了 `站点/模型` | 若该站点已无可用账号，反代会直接改派到有额度的站点（日志会写明），不必改客户端 |

可以手动禁用某个账号、重置它的失败计数，或改备注名。

## 七、还是要不到答案时

收集这三样东西再提问，能省掉大量来回：

1. `node status.mjs` 的输出
2. 控制台「实时日志」里对应那几行
3. 客户端报错的**原文**

> 提交 issue 前记得**把 API Key、uid、账号昵称打码**。
